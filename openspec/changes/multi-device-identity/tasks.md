- [x] 4.6 **Scope the event log store per root identity.** Found while implementing 4.4/4.5; not covered by any spec requirement, and a privacy bug as currently specified. The store is a flat `eventlog/<device_pk>.jsonl` directory with no identity binding, and log entries carry no `root_pk`. So: an existing single-device install upgrades (becoming its own identity, backfilling its history into its own log per 4.4), and is later QR-linked into a *different* identity. Its pre-link entries are authored by its own device key — which the new identity's root has now certified — so they verify, chain correctly, and are advertised in its sync vector. The user's entire previous private message history folds into the new identity and replicates to every one of its devices. Nothing in the sync session, the store, or the fold prevents this: they validate signature, seq continuity and `prev_hash`, but never "was this entry authored while its device was a member of *this* identity". Fix: namespace the store as `eventlog/<root_pk_hex>/<device_pk>.jsonl`, so enrolling into an identity starts a fresh log set and the displaced identity's data stays on disk untouched (which also gives 3.5b its answer for free). Rejected alternatives: clearing the log on enrollment (destructive, and loses the data 3.5b may want archived); adding a `root_pk` field to the entry layout (a wire-format break, and the cross-language vectors in 2.4 would all need regenerating). Needs the same treatment in the Rust `LogStore`, and a spec requirement added to `account-sync` at archive time (9.5)

## 6. Device linking flows

- [x] 6.1 App (new device): "Link to existing identity" entry in onboarding + settings — generate node key, show `azl` QR/string, accept `azula/link/0` dial, show verification words, apply `LinkGrant` (cert + bundle: root pk, certs, revocations, contacts snapshot, mailbox hint)
- [x] 6.2 App (root-holding device): scan/paste `azl`, dial, verification-words + role confirmation UI, issue cert, send `LinkGrant`, append `device_add`
- [x] 6.3 App: device management screen — list device set from the fold, rename display names locally, revoke (root holders only) appending `device_revoke`
- [x] 6.4 CLI: `azula link [--name] [--mailbox]` per `CLI Device Enrollment` (persist node key + cert + bundle under a new identity name, print QR via `qr.rs`, print verification words)
- [x] 6.6 **Make the `azl` link QR actually scannable.** Found verifying 6.1/6.2. The spec says the new device shows the payload "as a QR and copyable string" and "a root-holding device **scans** it" — 6.1 renders the QR, but it encodes the bare `azl…` string, the app has no QR scanner anywhere (`link/src/dev/azula/link/Qr.kt` is an encoder only; the two `camera` hits in the tree are incidental comments about display cutouts), and 6.2 shipped paste-only. So a phone camera pointed at the code yields plain text and no way to act on it: the QR is decorative and copy-paste is the only working path. Cheapest fix, and consistent with how invites already work: wrap the payload in a deeplink (`https://azula.app/l/<payload>` + `azula://l?c=<payload>`), add the route to azula-site, teach `link/src/dev/azula/link/DeepLink.kt` to parse it, and render *that* as the QR — the phone's own camera app then opens azula directly, with no in-app scanner needed. The alternative, a real in-app scanner (CameraX on Android, AVFoundation on iOS, plus permission flows), is a much larger platform-specific undertaking and buys little over the deeplink route
- [x] 6.5 Enforce revocation everywhere certs are checked (sync hello, known-peer gate, link) and include the revocation set in bundles and sync — **Rust side done**; Kotlin side outstanding. Two real gaps were found and fixed on the Rust side, both worth mirroring in Kotlin: (a) the revocation set was a snapshot taken from the `IdentityBundle` at process start, so a `device_revoke` arriving later via ordinary sync was stored but never enforced — violating the spec's `Own devices enforce revocation after sync` scenario; fixed with `LogStore::device_revocations()`, merged live per session. (b) the link flow persisted a `LinkGrant`'s certificate with no verification at all; fixed with `verify_granted_cert` (decodes, verifies signature + expiry, binds to this device's own key, not already revoked)
