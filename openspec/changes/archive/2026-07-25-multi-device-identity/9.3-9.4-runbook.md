# 9.3 / 9.4 manual verification runbook

Both remaining tasks need real hardware. Everything else in this change is
implemented and verified by the whole-project `./check` and `cargo test`. This
file is the executable plan for the two on-device passes, written so a later
session or a human can run them without reconstructing the context.

## Prerequisites (shared)

- A built `azula-cli` binary from the `multi-device-identity` branch (`cargo
  build` in the azula-cli worktree).
- `jvm-app` runnable on the desktop: `./kotlin build -m jvm-app` in the
  azula-app worktree, then run it.
- The azula-app `multi-device-identity` branch merged or checked out for the
  build under test.

## 9.4 — forward migration (BLOCKED on Play signing)

**Status: cannot run locally. Fixture preserved.** The Pixel's `app.azula`
(installed 2026-07-20, versionName 0.0.0) is signed with the Google Play App
Signing key `9A:CD:CD:2B:…`. Neither the local debug key (`6B:52…`) nor the
upload keystore (`69:63…`, `~/.keystores/azula-upload.jks`) matches it, so no
locally-built APK can `install -r` over it, and uninstalling would destroy the
one authentic pre-change fixture.

To run it when you next ship:
1. Note the fixture's current state first: open `app.azula` on the Pixel,
   record the recovery phrase (Settings → reveal), the endpoint id / "my code", and
   a couple of existing conversations with their message history.
2. Build the signed release AAB with the upload key
   (`android-app/keystore.properties` from the item "azula-app upload keystore
   password", then `.github/scripts/enable_signing.sh` — see
   `openspec/specs/release/design.md`) and push to **Play internal**.
3. Update `app.azula` on the Pixel **through Play** (so Google re-signs with the
   same `9A:CD…` key the install already has).
4. Verify after the update:
   - Recovery phrase is **unchanged** (same 24 words).
   - Endpoint id / "my code" is **unchanged** (legacy peers still recognise it).
   - All pre-existing conversations and their message history are **still
     present** — this is the one-shot backfill (task 4.4) running against real
     old data for the first time; a persisted flag means it runs exactly once.
   - Fresh sanity: send/receive with an existing contact still works.
5. Rollback half is **dropped** — no pre-change APK is available to downgrade
   to, and Android 17 can't back the install up. Record as "not performed".

The forward-migration *logic* is already covered by
`mock-support/test@jvm/AccountSyncWiringTest.kt`,
`network-real/test@jvm/RootSecretMigrationTest.kt`, and
`core/test/RootIdentityMigrationTest.kt`. What the on-device pass adds is
confidence against **real** old on-disk state, which no test can synthesise
honestly.

## 9.3 — three-endpoint end-to-end (HELD)

**Status: not run this session (user held the phone).** Runnable without
touching the 9.4 fixture by building a separate-package variant.

1. **Phone build (fixture-safe):** override `applicationId` to
   `app.azula.mdtest` in `android-app/module.yaml`, build a local-debug-signed
   debug APK, `adb install` it. It installs alongside the untouched `app.azula`.
   (Do NOT install over `app.azula` — see 9.4.)
2. **Desktop:** run `jvm-app` on the Mac.
3. **Mailbox:** `azula link --mailbox` on the Mac (confirm on the phone/desktop
   root-holding side), then `azula mailbox`.
4. **The pass:**
   - Link the desktop to the phone's identity (QR or paste the `azl…` string —
     note the QR only camera-follows once the azula-site `/l/` route is
     deployed; until then use the copyable string).
   - Message a **legacy** peer (an old build, no cert) and confirm endpoint-id
     keying and unaffected behaviour.
   - Message a **certified** peer and confirm root-pk keyed conversation.
   - Kill the phone (force-stop). Have a contact send to the identity; confirm
     the **mailbox** accepts and stores it (`message_in`).
   - Relaunch the phone; confirm it converges (history + the new message arrive
     via sync) and the unread badge clears **once** (not per-device).
5. **Watch specifically** (unit tests don't cover these):
   - Bootstrap-prefers-mailbox: the identity bundle's `mailbox` hint is
     currently always `null` (no app-side mailbox tracking yet), so a
     just-linked device finding the mailbox relies on sibling dial, not the
     hint. Confirm convergence still happens.
   - The single-unread-badge-clear depends on `read_marker` being the only
     read-state channel — confirm no second channel resurfaces on device.
