- [x] 4.6 **Scope the event log store per root identity.** Found while implementing 4.4/4.5; not covered by any spec requirement, and a privacy bug as currently specified. The store is a flat `eventlog/<device_pk>.jsonl` directory with no identity binding, and log entries carry no `root_pk`. So: an existing single-device install upgrades (becoming its own identity, backfilling its history into its own log per 4.4), and is later QR-linked into a *different* identity. Its pre-link entries are authored by its own device key — which the new identity's root has now certified — so they verify, chain correctly, and are advertised in its sync vector. The user's entire previous private message history folds into the new identity and replicates to every one of its devices. Nothing in the sync session, the store, or the fold prevents this: they validate signature, seq continuity and `prev_hash`, but never "was this entry authored while its device was a member of *this* identity". Fix: namespace the store as `eventlog/<root_pk_hex>/<device_pk>.jsonl`, so enrolling into an identity starts a fresh log set and the displaced identity's data stays on disk untouched (which also gives 3.5b its answer for free). Rejected alternatives: clearing the log on enrollment (destructive, and loses the data 3.5b may want archived); adding a `root_pk` field to the entry layout (a wire-format break, and the cross-language vectors in 2.4 would all need regenerating). Needs the same treatment in the Rust `LogStore`, and a spec requirement added to `account-sync` at archive time (9.5)

- [x] 6.6 **Make the `azl` link QR actually scannable.** Found verifying 6.1/6.2. The spec says the new device shows the payload "as a QR and copyable string" and "a root-holding device **scans** it" — 6.1 renders the QR, but it encodes the bare `azl…` string, the app has no QR scanner anywhere (`link/src/dev/azula/link/Qr.kt` is an encoder only; the two `camera` hits in the tree are incidental comments about display cutouts), and 6.2 shipped paste-only. So a phone camera pointed at the code yields plain text and no way to act on it: the QR is decorative and copy-paste is the only working path. Cheapest fix, and consistent with how invites already work: wrap the payload in a deeplink (`https://azula.app/l/<payload>` + `azula://l?c=<payload>`), add the route to azula-site, teach `link/src/dev/azula/link/DeepLink.kt` to parse it, and render *that* as the QR — the phone's own camera app then opens azula directly, with no in-app scanner needed. The alternative, a real in-app scanner (CameraX on Android, AVFoundation on iOS, plus permission flows), is a much larger platform-specific undertaking and buys little over the deeplink route
- [x] 6.5 Enforce revocation everywhere certs are checked (sync hello, known-peer gate, link) and include the revocation set in bundles and sync — **Rust side done**; Kotlin side outstanding. Two real gaps were found and fixed on the Rust side, both worth mirroring in Kotlin: (a) the revocation set was a snapshot taken from the `IdentityBundle` at process start, so a `device_revoke` arriving later via ordinary sync was stored but never enforced — violating the spec's `Own devices enforce revocation after sync` scenario; fixed with `LogStore::device_revocations()`, merged live per session. (b) the link flow persisted a `LinkGrant`'s certificate with no verification at all; fixed with `verify_granted_cert` (decodes, verifies signature + expiry, binds to this device's own key, not already revoked)

- [x] 6.7 **FIXED + VERIFIED ON DEVICE (2026-07-24).** Fix: the dialer writes one raw newline immediately after opening the bi-stream, unblocking the peer's `accept_bi()`; skipped by both frame readers (Rust `read_frame` already skipped blanks; Kotlin `receiveFrameLine` now does too, needed for app-to-app linking). No wire-format change, so the task-2.4 cross-language vectors stay valid. Added `link_handshake_completes_over_a_real_quic_connection` (two real iroh endpoints) — the regression guard whose absence allowed this. **On-device confirmation:** phone (Kotlin) and `azula link` (Rust) both displayed the identical verification words `chief · load · ancient · above`, the grant completed ("Linked! Certificate and identity bundle saved"), and the phone's event log went 1→2 entries, both `kind=06 device_add`. ORIGINAL BUG: the `azula/link/0` handshake deadlocks over a real QUIC connection.** Device linking between the Android app and `azula link` never completes: 3/3 attempts timed out with `MultipathNotNegotiated` + "Accepting incoming connection ended with error: timed out"; a 4th got as far as the CLI printing `Verification words: believe fashion blind width` and then hung, with the phone stuck on "Connecting…". Control: a plain `azula serve --term-only` over the *same* network path connected instantly (`direct · 16ms`), so this is specific to the link ALPN, not connectivity.
  **Root cause:** the spec has the **new device accept** and the **root-holding device dial**, and makes `LinkHello` (sent by the new device) the first frame — so the *accepting* side must speak first. But QUIC's `accept_bi()` does not return until the **dialer** opens a stream **and writes data on it**. The dialer (phone) opens the stream then blocks reading `LinkHello`; the accepter (CLI, `src/link.rs:150`) blocks in `accept_bi()` awaiting bytes the phone will not send until it has read `LinkHello`. Deadlock. `src/term.rs:1278` documents this exact gotcha ("`accept_bi`, which blocks until the client sends data") and the working term ALPN has the dialer send first.
  **Why the tests missed it:** both languages' link-protocol tests run over in-memory duplex streams (deliberately, for testability) which have no "stream-open doesn't transmit until first write" semantics — both directions are live immediately. The protocol *logic* is correct and well covered; the *transport wiring* is what's broken. Any fix should add a real-transport test, since an in-memory one cannot reproduce this.
  **Fix options:** (a) have the dialer (root-holder) send an opening frame first — cleanest, matches term/0's working shape, but changes the wire order so `proto.rs`+`Protocol.kt` and both sides move in lockstep; (b) keep the frame order and have the dialer write a zero-length/priming payload immediately after `open_bi()` to unblock the peer's `accept_bi()`; (c) invert the roles so the root-holder accepts and the new device dials — largest change, and the `azl` payload already carries the new device's ticket precisely so the root-holder can dial it. Also re-check `MultipathNotNegotiated`, which appeared on the failing path but not the working one.
  Fixing this unblocks 9.3 stages 2–5, which are all still unverified on hardware.

- [x] 9.6 **FIXED FOR ANDROID (2026-07-24); iOS and desktop gap recorded as 9.7.** `setForeground` now re-dials siblings on the false->true edge only, with a `siblingDialsInFlight` per-device guard (mirroring `ConversationState.reconnecting`'s add-before-launch/clear-in-finally convention) so repeated or near-simultaneous resumes can't stack dials. Task 5.4's bounded `livePush = false` catch-up is untouched — this changes *when* we dial, not how the session runs. ORIGINAL: Sibling sync only triggers on cold start / transport re-bind, not while the app is merely running.** Found by the 9.3 hardware pass: backgrounding the phone and returning to it did NOT trigger a sync for ~9 minutes (the mailbox saw zero inbound connections); a full `am force-stop` plus cold relaunch triggered it immediately and converged. Cause: `ConnectService.reconnectSiblings()` is reachable only from `transport.onCameOnline` (which fires on a re-bind) and from the one-shot call at the end of `start()`. An app that stays resident never re-binds, so it never re-dials its siblings. This undercuts the change's own motivating scenario — "read it on the laptop and the phone's badge clears" — because phones are backgrounded almost all the time, so devices would silently drift until something forces a cold start. Options: (a) re-dial siblings on app foreground/resume (Android `ON_RESUME`, desktop window focus) as well as on re-bind; (b) a periodic re-dial while resident, bounded and backing off; (c) keep sync sessions long-lived and rely on `runSyncSession`'s live-push phase — note task 5.4 deliberately uses `livePush = false` bounded catch-up for sibling dials to avoid parking a coroutine per sibling, so (c) needs that trade-off revisited. Whichever is chosen, it needs an on-device check, since this is exactly the class of behaviour a green `./check` cannot evidence (see testing/design.md, the link/0 lesson).
